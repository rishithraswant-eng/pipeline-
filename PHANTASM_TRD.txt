SECTION 1 — SYSTEM OVERVIEW AND ARCHITECTURE SUMMARY
================================================================================

1.1 WHAT PHANTASM IS
─────────────────────

PHANTASM is a cognitive honeypot — a generative, adaptive, AI-powered
deception platform that simulates an Indian BFSI enterprise network, profiles
the human operator attacking it in real time, reshapes itself to maximise
their engagement, and produces a CERT-In compliant threat intelligence
dossier automatically when the session ends.

It is deployed as a single-machine system on an Ubuntu 22.04 laptop.
All components run locally. No cloud infrastructure is required during the demo.

1.2 THREE LAYERS
─────────────────

  LAYER 1 — SHADOWMESH
    What it is: A generative fake network that appears to be a real Indian
    mid-tier bank's internal infrastructure. 15+ fake hosts across 3 subnets.
    Packet-correct responses via NFQueue. Background traffic via pre-trained GAN.

  LAYER 2 — MIRRORTRAP
    What it is: A real-time AI profiling engine that reads every command the
    attacker issues and builds a 4-dimensional psychological profile: expertise
    level, inferred objective, operational state, and APT attribution.

  LAYER 3 — ADAPTIVE FEEDBACK LOOP
    What it is: A rule-based controller that reads MirrorTrap's profile and
    mutates ShadowMesh topology dynamically — materialising crown jewel nodes
    targeted at the specific attacker type detected, then generating a
    CERT-In formatted PDF dossier the moment the session ends.

1.3 END-TO-END DATA FLOW (SUMMARY)

  Attacker sends probe packet
    → NFQueue intercepts at kernel
      → sm_core dispatches to service emulator
        → Protocol-correct fake response returned to attacker
          → Event published to Redis channel "sm:events"
            → mt_engine consumes event, classifies command, updates profile
              → Profile published to Redis "mt:profile"
                → fc_controller evaluates triggers, optionally issues mutation
                  → api_server bridges profile to WebSocket
                    → React frontend renders animated update in <100ms
  [Session Ends]
    → session_mgr aggregates session record
      → de_engine formats LLM prompt, calls Claude API
        → Narrative returned, embedded in Jinja2 HTML template
          → WeasyPrint renders PDF
            → Dashboard receives dossier_ready event
              → Analyst downloads and optionally prints

2.1 BACKEND RUNTIME

  Python 3.11.x
    Why: asyncio improvements, faster CPython, required by Transformers 4.38+.
    Install: apt install python3.11 python3.11-venv python3.11-dev

  FastAPI 0.110.x
    Why: async-native, built-in WebSocket support, Pydantic v2 models, auto
    OpenAPI docs. Zero-config CORS. Fastest Python web framework for this use.
    Install: pip install fastapi==0.110.0

  Uvicorn 0.27.x
    Why: ASGI server for FastAPI. Supports WebSocket. Low latency.
    Install: pip install uvicorn[standard]==0.27.1

  aiohttp 3.9.x
    Why: Async HTTP client for Claude API calls with timeout control and retry.
    Install: pip install aiohttp==3.9.3

  asyncio (stdlib)
    Why: All PHANTASM components are async. Single event loop per process.
    No additional install.

2.2 NETWORKING / PACKET ENGINE

  Scapy 2.5.0
    Why: The only Python library for crafting custom protocol packets at byte
    level. Used for crafting fake SSH banners, SMB responses, ARP packets,
    and the background traffic emission layer.
    Install: pip install scapy==2.5.0

  libnetfilter_queue (system library)
    Why: Linux kernel netfilter hook that routes incoming packets to a userspace
    Python process for custom handling and response. Required for ShadowMesh
    to intercept and respond to Nmap probes without being a real OS.
    Install: sudo apt install libnetfilter-queue-dev python3-dev
    Python binding: pip install nfqueue-bindings==0.6

    IMPORTANT: NFQueue requires root/CAP_NET_ADMIN. ShadowMesh process must
    run as root or with sudo. This is acceptable for a controlled demo system.

  impacket 0.11.0
    Why: Microsoft protocol implementations (SMB2, LDAP, Kerberos) used as
    reference and partial implementation basis for service emulators.
    Install: pip install impacket==0.11.0

2.3 MESSAGE QUEUE / STATE BUS

  Redis 7.2.x (server, via Docker)

    Redis channels. Session state hashes. ICI sliding window lists. Mutation

4.3 NETWORK INTERFACE SETUP FOR SHADOWMESH

  ShadowMesh intercepts packets on a designated dummy interface.
  This prevents ShadowMesh from interfering with the real management interface.

    # Create dummy interface:
    ip link add shadowmesh0 type dummy
    ip link set shadowmesh0 up
    ip addr add 192.168.10.1/24 dev shadowmesh0

    # Add alias addresses for all three subnets:
    ip addr add 192.168.20.1/24 dev shadowmesh0
    ip addr add 192.168.30.1/24 dev shadowmesh0

    # NFQueue routing rule — redirect ALL incoming traffic on shadowmesh0
    # to NFQueue queue number 1:
    iptables -I INPUT -i shadowmesh0 -j NFQUEUE --queue-num 1
    iptables -I FORWARD -i shadowmesh0 -j NFQUEUE --queue-num 1

  The attacker terminal (on the same machine) points at 192.168.10.x addresses.
  Traffic routes through the shadowmesh0 dummy interface and hits NFQueue.

  NOTE: If running attacker and defender on SEPARATE machines, replace the
  dummy interface with a real secondary NIC. Route attacker traffic through
  a switch/hub to the secondary NIC. All other configuration remains identical.

================================================================================
SECTION 5 — COMPONENT 1: SHADOWMESH CORE (sm_core.py)
================================================================================

5.1 PURPOSE

ShadowMesh is the fake enterprise network. It is the first thing an attacker
interacts with. Everything it does must be believable. If ShadowMesh fails
to fool the attacker, the entire system is useless.

sm_core.py is the orchestrator. It manages:
  - The topology state (which fake hosts exist, what they serve)
  - The NFQueue hook (intercept and route incoming packets)
  - The per-service response dispatcher
  - The background traffic emission scheduler
  - The mutation directive consumer (Redis "sm:mutations" channel)
  - The topology REST API (localhost:8001)

5.2 TOPOLOGY GENERATOR (sm_topology.py)

Called at startup. Generates the fake network procedurally.

  HOST GENERATION LOGIC:
    1. Load bfsi_hostnames.json — pool of realistic Indian bank hostname patterns.
    2. Assign hostnames deterministically to role slots:
         domain_controller:   dc-auth-prod.{domain}
         database_server:     findb-primary-01.{domain}
         web_server:          webportal-01.{domain}
         file_server:         filesvr-corp-01.{domain}
         payment_gateway:     pgw-mfss-01.{domain}
         hr_system:           hrms-db-prod.{domain}
         workstation (×8):    ws-{dept}-{seq}.{domain}
         proxy:               internet-gw-01.{domain}
         management:          mgmt-console.{domain}
    3. Assign IP addresses in 192.168.{10/20/30}.x ranges:
         10.x = user VLAN (workstations)
         20.x = server VLAN (databases, web, file, HR, payment)
         30.x = management VLAN (DC, management console, gateway)
    4. Assign OS fingerprints from os_fingerprints.json:
         Windows Server 2019: TTL=128, TCP window=65535, MSS=1460
         Windows 10 Pro:      TTL=128, TCP window=64240, MSS=1460
         Ubuntu 22.04:        TTL=64,  TCP window=29200, MSS=1460
         Cisco IOS 15.x:      TTL=255, TCP window=4128,  MSS=1460
    5. Assign services to each host based on role (see Section 6).
    6. Assign response latency baselines:
         Servers:     gaussian(μ=2.0ms, σ=0.6ms)
         Workstations: gaussian(μ=5.0ms, σ=1.5ms)
         Network gear: gaussian(μ=0.5ms, σ=0.15ms)
    7. Serialise to topology JSON and store:
         a. Redis key: "topology:current" (JSON string)
         b. SQLite: topology_snapshots table, type='base'
         c. fake_hosts table: one row per generated host

  GRAPH EDGE GENERATION:
    Edges represent network relationships visualised in D3.
    Generated alongside hosts:
      workstations → domain_controller (ldap_auth)
      workstations → web_server (http)
      database_server → domain_controller (ldap_auth)
      payment_gateway → database_server (db_link)
      file_server → domain_controller (ldap_auth)
    Stored in topology JSON under "edges" array.

5.3 NFQUEUE PACKET INTERCEPTION

  How it works:
    iptables routes all traffic on shadowmesh0 to NFQUEUE queue 1.
    nfqueue-bindings Python library binds to queue 1 in userspace.
    sm_core.py receives each packet as a callback.

  Packet processing loop (sm_core.py):

    from netfilterqueue import NetfilterQueue
    from scapy.all import IP, TCP, UDP

    def packet_callback(pkt):
        scapy_pkt = IP(pkt.get_payload())
        dst_ip = scapy_pkt[IP].dst
        dst_port = scapy_pkt[TCP].dport if TCP in scapy_pkt else None
        protocol = 'TCP' if TCP in scapy_pkt else 'UDP'

        # Look up the host in topology
        host = topology_state.get_host(dst_ip)
        if host is None:
            pkt.drop()   # IP not in our fake network — drop silently
            return

        # Look up the service emulator for this port
        emulator = emulator_registry.get(dst_port)
        if emulator is None:
            pkt.drop()   # Port not emulated — silently drop
            return

        # Generate response (runs sync; emulator must be fast)
        response_pkt = emulator.handle(scapy_pkt, host)

        # Apply latency jitter BEFORE returning response
        latency = host.sample_latency()   # gaussian sample
        time.sleep(latency / 1000.0)

        # Accept original packet (consumed) and send response
        pkt.accept()
        send(response_pkt, verbose=False)

        # Publish event to Redis (async in background task)
        asyncio.run_coroutine_threadsafe(
            redis_pub.publish("sm:events", build_event(scapy_pkt, host)),
            main_event_loop
        )

    nfq = NetfilterQueue()
    nfq.bind(1, packet_callback)
    nfq.run()    # Runs in dedicated thread alongside asyncio loop

  LATENCY JITTER IMPLEMENTATION:
    Each fake_host has a baseline_ms and jitter_pct (default 0.30).
    Sample at each packet: scipy.stats.norm.rvs(loc=baseline, scale=baseline*jitter_pct)
    Clamp to [0.1ms, baseline * 3.0] to prevent unrealistic values.
    This ensures RTT standard deviation passes timing fingerprint tests.

6.1 BASE EMULATOR (base_emulator.py)

  Abstract class all emulators inherit from:

    class BaseEmulator:
        PORTS: list[int]        # Ports this emulator handles
        PROTOCOL: str           # "TCP" or "UDP"

        def handle(self, pkt: Packet, host: FakeHost) -> Packet:
            """Build and return a Scapy response packet."""
            raise NotImplementedError

        def build_response(self, src_ip, src_port, dst_ip, dst_port,
                          payload: bytes) -> Packet:
            """Utility: build IP/TCP response with given payload."""
            return (IP(src=dst_ip, dst=src_ip) /
                    TCP(sport=dst_port, dport=src_port,
                        flags="PA", seq=..., ack=...) /
                    Raw(load=payload))

6.2 SSH EMULATOR (ssh_emulator.py)

  PORTS: [22]
  Handles: TCP SYN (respond with SYN-ACK), then SSH version banner.

  Banner format (matches host declared OS):
    Windows Server 2019 host: "SSH-2.0-OpenSSH_for_Windows_8.6\r\n"
    Linux host:               "SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.6\r\n"

  Key exchange initiation:
    Returns SSH_MSG_KEXINIT packet with:
    - kex_algorithms: curve25519-sha256, ecdh-sha2-nistp256
    - server_host_key_algorithms: ssh-rsa, ecdsa-sha2-nistp256
    - encryption_algorithms_client_to_server: aes256-ctr
    After key exchange, connection hangs on authentication — never completes.
    This is sufficient to defeat Nmap -sV and banner grabbers.

  Command capture:
    If the attacker completes SSH auth (by any credential — all accepted),
    the emulator enters a fake shell session. All input lines are captured
    and published to "sm:events" as command events. Output is fabricated
    based on the command type (see ad_emulator for AD commands, db_emulator
    for SQL commands, standard shell responses for all others).

SECTION 7 — COMPONENT 3: GAN TRAFFIC GENERATOR (sm_traffic_gan.py)
================================================================================

7.1 PURPOSE

Real enterprise networks have ambient traffic. A silent honeypot network
betrays itself to any attacker who runs passive traffic analysis (Wireshark,
tcpdump). ShadowMesh must generate background traffic that matches statistical
profiles of a 100-employee bank network.

7.2 DCGAN MODEL

  Pre-trained offline on CICIDS-2023 and UNSW-NB15 datasets.
  Model generates synthetic packet feature vectors (not raw bytes).
  These vectors are post-processed into Scapy packets and emitted.

  Architecture: DCGAN generator with 100-dim latent vector input.
  Output: 84-feature packet descriptor (mapped to actual Scapy fields).
  Model file: /backend/models/dcgan_traffic/generator.pt
  Load at startup: torch.load("generator.pt", map_location="cpu")

  Traffic types generated:
    - NTP sync packets (UDP/123) from all fake servers to 192.168.30.x (fake NTP)
    - DNS queries (UDP/53) from workstations to domain controller
    - SMB keep-alive (TCP/445) between random server pairs
    - LDAP authentication attempts (TCP/389) from servers to DC
    - HTTPS egress (TCP/443) from workstations to fake internet gateway

7.3 EMISSION SCHEDULE

  Background coroutine runs every 3 seconds:
    1. Sample 10-30 traffic events from DCGAN
    2. For each event: build Scapy packet from feature vector
    3. Emit via raw socket on shadowmesh0 interface
    4. Traffic visible on Wireshark as real ambient enterprise traffic

  Volume calibration: CICIDS-2023 profile for 100-employee enterprise:
    ~450 packets/minute background baseline.
    Generator targets 400-500 packets/minute.

7.4 FALLBACK (if PyTorch/GPU too slow)

  If inference time exceeds 200ms per batch:
    Replace DCGAN with pre-generated Scapy packet sequence stored in a
    PCAP file. Loop the PCAP file, replaying with adjusted timestamps.
    pcap_replay.py: reads traffic.pcap, adjusts timestamps, re-emits.
    This is functionally equivalent for demo purposes.

8.3 ATT&CK CLASSIFICATION (mt_classifier.py)

  Model: Fine-tuned BERT-base-uncased converted to ONNX (INT8 quantised).
  Task: Multi-label classification (one command → 1-3 technique IDs).
  Labels: 196 MITRE ATT&CK v14 technique IDs.

  Inference pipeline:
    1. Normalise command: lowercase, strip extra whitespace, max 512 tokens.
    2. Tokenise with BERT tokenizer (loaded from /models/bert_attack/tokenizer/).
    3. Run ONNX inference:
         session = ort.InferenceSession("bert_attack/model.onnx")
         outputs = session.run(None, {
             "input_ids": input_ids,
             "attention_mask": attention_mask
         })
    4. Apply sigmoid activation to logits.
    5. Threshold at 0.5 for primary technique, 0.3 for secondary.
    6. Map indices to technique IDs using label_map.json.
    7. Return: [{"technique_id": "T1046", "confidence": 0.91, "is_primary": True}]

  Target latency: <400ms on 4-core CPU (tested with INT8 quantisation).

  Keyword fallback (if model confidence < 0.4 for all labels):
    Rule-based keyword matcher using att&ck_v14.json keyword fields.
    Maps known tool names and keywords to technique IDs with confidence=0.65.
    Ensures 100% coverage (never "Unknown" for well-known commands).

8.4 EXPERTISE SCORING (mt_expertise.py)

  Maintained as a rolling score, updated every 5 commands.
  Expertise can only increase (never downgrade) within a session.

  Scoring signals and weights:
    Command complexity (30%):
      - Pipe count per command: +5 pts per pipe
      - Flag count: +3 pts per flag
      - Subshell usage ($(), backticks): +10 pts
      - Redirection operators (>, |, >>): +3 pts each
      - Base64/encoded arguments: +15 pts

    Tool sophistication (30%):
      - Native OS tools only (net, ipconfig, dir): 0 pts
      - Single-purpose well-known tools (Nmap, Mimikatz): +20 pts
      - Framework tools (Cobalt Strike, PowerSploit, Empire): +30 pts
      - Custom/novel tooling (unknown binary names): +25 pts

    Sequencing logic (20%):
      - Commands follow logical recon→access→lateral→collect pattern: +20 pts
      - Commands appear random or templated: 0 pts
      - Error-correction: modified retry after failure: +15 pts, exact repeat: 0 pts

    Privilege escalation speed (20%):
      - First priv-esc attempt within 5 commands of access: +25 pts
      - 5-15 commands: +15 pts
      - >15 commands: +5 pts

  Score thresholds → expertise levels:
    0-25:   Script Kiddie
    25-50:  Intermediate
    50-75:  Advanced
    75+:    APT-Grade

8.5 OBJECTIVE INFERENCE (mt_engine.py)

8.6 OPERATIONAL STATE ESTIMATION (mt_timing.py)

  ICI (Inter-Command Interval) computed from timestamps.
  Maintained as a sliding window of last 20 ICI values.

    ici_window = deque(maxlen=20)

    stddev_ici = statistics.stdev(ici_window) if len > 1 else 0

    elif mean_ici < 3000 and trend < -100:     → "stressed"
    elif stddev_ici > mean_ici * 0.8:          → "disoriented"

    Annotation: "Stress onset — cadence acceleration {delta}%"
    Written to stress_timeline table.

10.2 SESSION LIFECYCLE

    4. Publish "session_started" event to "phantasm:dashboard"
    5. Start flush_worker coroutine (every 5 seconds)
    6. Start temporal_aging coroutine (every 60 seconds)

  FLUSH WORKER (every 5 seconds):
    Reads buffered commands from in-memory list (appended by mt_engine).
    Batch-inserts into commands table (one INSERT with VALUES (...),(...),...).
    Batch-inserts technique links into command_techniques table.
    Batch-inserts host interactions into host_interactions table.
    Clears buffer after successful insert.
    Rationale: Batching prevents SQLite lock contention under rapid command flow.

  TEMPORAL AGING WORKER (every 60 seconds):
    Updates last_logon timestamps on 5-12% of ad_synthetic_users (random sample).
    Inserts 3-7 new db_synthetic_records in customer_accounts (simulating transactions).
    Appends fake entries to any served process_listing objects.
    Rotates Windows Event Log entries in served synthetic_data_objects.
    This prevents sophisticated attackers from noticing a frozen synthetic world.

  SESSION END:
    Trigger: [END SESSION] button in dashboard OR attacker disconnect detection.
    1. Set sessions.session_state = 'ended', sessions.ended_at = NOW()
    2. Compute sessions.duration_seconds
    3. Compute sessions.dwell_multiplier = duration / dwell_baseline
    4. SYNC flush: write ALL remaining buffered events to SQLite (no 5-second wait)
    5. Commit SQLite transaction
    6. Call de_engine.generate_dossier(session_id)
    7. Publish "session_ended" to "phantasm:dashboard"

  DISCONNECT DETECTION:
    NFQueue callback sets a "last_packet" Redis key with 30-second TTL.
    A background task checks every 10 seconds: if key expired → attacker gone.
    Triggers automatic session end via the same flow above.

  GET /api/sessions/{session_id} → full session record with all commands
  Implemented in api_server.py, reads from SQLite sessions table.

12.4 WEBSOCKET / SOCKET.IO BRIDGE

  On API server startup, a background coroutine subscribes to all relevant
  Redis channels and forwards events to connected Socket.io clients:

    @sio.event
    async def connect(sid, environ):
        # Send current state snapshot to newly connected client
        topology = await redis.get("topology:current")
        profile = await redis.hgetall(f"session:{active_session_id}:profile:current")
        await sio.emit("state_snapshot", {"topology": topology, "profile": profile}, to=sid)

    async def redis_to_socketio_bridge():
        pubsub = redis.pubsub()
        await pubsub.subscribe("phantasm:dashboard")
        async for message in pubsub.listen():
            if message["type"] == "message":
                event_data = json.loads(message["data"])
                await sio.emit(event_data["type"], event_data)

  Events emitted to frontend (see Section 17 for full protocol):
    command_received, profile_update, topology_mutation, session_started,
    session_ended, dossier_ready, system_health_update

12.5 HEALTH HEARTBEAT WRITER

  Each component publishes its heartbeat to Redis every 5 seconds:
    HSET phantasm:system:health shadowmesh_ts {unix_timestamp}
    HSET phantasm:system:health mirrortrap_ts {unix_timestamp}

  api_server reads these and computes status:
    delta = now - component_ts
    status = "ok" if delta < 15 else "degraded" if delta < 30 else "down"

  Emits "system_health" event to frontend every 10 seconds.

14.3 KEY-VALUE STATE

    Read by: api_server /api/topology, frontend on reconnect

    Written by: session_mgr
    Read by: api_server health endpoint

  session:{session_id}:profile:current
    HASH fields: all 4 profile dimensions + timing stats + engagement
    Written by: mt_engine on each profile publish
    Read by: api_server on WebSocket reconnect for state restore

    Written by: each component's heartbeat loop (every 5 seconds)
    Read by: api_server health endpoint

  session:{session_id}:synthetic:available:{object_type}

    Written by: init_synthetic.py and mutation coroutines

SECTION 15 — STORAGE ARCHITECTURE: SQLITE (TIER 2)

15.1 DATABASE LOCATION AND CONFIGURATION

  File: /data/phantasm.db
  Connection: aiosqlite.connect("/data/phantasm.db")
  Pragmas set on every connection:
    PRAGMA journal_mode = WAL;
    PRAGMA synchronous = NORMAL;
    PRAGMA cache_size = -64000;    -- 64MB page cache
    PRAGMA foreign_keys = ON;
    PRAGMA temp_store = MEMORY;

  WAL mode is critical: allows concurrent async read/write without blocking.
  Without WAL, the flush_worker's writes would block api_server's reads.

15.3 KEY DOSSIER QUERIES (from queries.py)

  All queries use parameterised statements. No string interpolation in SQL.

  Query 1 — Session Overview:
    SELECT duration_seconds, total_commands, unique_techniques, engagement_score,
           dwell_multiplier, attacker_source_ip, entry_protocol
    FROM sessions WHERE session_id = ?

  Query 2 — Techniques (aggregated):
    SELECT ct.technique_id, ct.technique_name, ct.tactic,
           MIN(c.session_elapsed_ms)/1000 AS first_observed_s,
           COUNT(*) AS occurrence_count
    FROM command_techniques ct
    JOIN commands c ON ct.command_fk = c.command_pk
    WHERE c.session_fk = (SELECT session_pk FROM sessions WHERE session_id = ?)
    GROUP BY ct.technique_id ORDER BY occurrence_count DESC

  Query 3 — Final Profile:
    SELECT * FROM operator_profiles
    WHERE session_fk = (SELECT session_pk FROM sessions WHERE session_id = ?)
    ORDER BY snapshot_at DESC LIMIT 1

  Query 4 — Stress Events:
    SELECT session_elapsed_s, ici_ms, stress_state, stress_annotation
    FROM stress_timeline
    WHERE session_fk = (SELECT session_pk FROM sessions WHERE session_id = ?)
    AND stress_state != 'normal'
    ORDER BY session_elapsed_s

  Query 5 — IOCs:
    SELECT ioc_type, ioc_value, ioc_port, ioc_protocol, context_command, confidence
    FROM iocs
    WHERE session_fk = (SELECT session_pk FROM sessions WHERE session_id = ?)
    ORDER BY ioc_type

  Query 6 — Assets Accessed:
    SELECT fh.hostname, fh.ip_address, fh.host_role,
           hi.interaction_type, hi.access_level, hi.interaction_depth,
           hi.commands_on_host, hi.data_exfil_attempted
    FROM host_interactions hi
    JOIN fake_hosts fh ON hi.host_fk = fh.host_pk
    WHERE hi.session_fk = (SELECT session_pk FROM sessions WHERE session_id = ?)
    AND hi.access_level != 'none'
    ORDER BY hi.commands_on_host DESC

  Query 7 — Mutations:
    SELECT trigger_condition, triggered_at, nodes_added_json, mutation_latency_ms
    FROM topology_mutations
    WHERE session_fk = (SELECT session_pk FROM sessions WHERE session_id = ?)
    ORDER BY triggered_at

SECTION 18 — AI/ML PIPELINE: MODELS, INFERENCE, AND QUANTISATION
================================================================================

18.1 MODEL 1 — BERT ATT&CK CLASSIFIER

  Base model: bert-base-uncased (HuggingFace hub)
  Fine-tuning: Multi-label classification on dataset of:
    - MITRE Caldera adversary emulation logs (labelled)
    - DARPA TC dataset attack sequences (labelled)
    - Manual annotation of 200+ cybersecurity commands
    - ATT&CK dataset from MITRE's own technique examples
  Output layer: Linear(768, 196) with sigmoid (196 = technique count in ATT&CK v14)
  Training: Done offline. Weights bundled with repo. No training at runtime.

  ONNX EXPORT (pre-demo, not at demo time):
    from optimum.onnxruntime import ORTModelForSequenceClassification
    model = ORTModelForSequenceClassification.from_pretrained(
        "bert_attack_finetuned", export=True
    )
    # INT8 quantisation for CPU speed:
    from onnxruntime.quantization import quantize_dynamic, QuantType
    quantize_dynamic("model.onnx", "model_int8.onnx", weight_type=QuantType.QInt8)

  Runtime inference: ONNX Runtime InferenceSession (see Section 8.3).
  Expected latency: 200-350ms on 4-core CPU (INT8 quantised).

18.2 MODEL 2 — DISTILBERT EXPERTISE CLASSIFIER

  Base model: distilbert-base-uncased
  Fine-tuning: 4-class classification (script_kiddie / intermediate / advanced / apt_grade)
  Dataset: Synthetic command sequences generated for each expertise level.
  Output layer: Linear(768, 4) with softmax.

  NOTE: For hackathon, the DistilBERT model is SUPPLEMENTARY to the heuristic
  scoring system (Section 8.4). The heuristic system is more interpretable
  and reliable for a demo. DistilBERT's output is weighted at 30% of final
  expertise score; heuristics are 70%.

  ONNX export and quantisation same process as BERT above.

18.3 MODEL 3 — DCGAN TRAFFIC GENERATOR

  Architecture: DCGAN generator (100-dim latent → 84-dim packet descriptor)
  Framework: PyTorch (kept as .pt file, not ONNX — inference is fast enough)
  Load at startup: gen = torch.load("dcgan_traffic/generator.pt", map_location="cpu")
  Inference: gen(torch.randn(BATCH_SIZE, 100)) — CPU inference
  Expected batch time: <50ms for 30-packet batch

18.4 ATT&CK GROUP VECTORS

  File: /backend/models/att&ck_vectors/group_vectors.npy
  Shape: (138, 196) — 138 named groups × 196 technique slots
  Value: binary (1 if group uses technique, 0 if not) from MITRE ATT&CK JSON
  Build script: python scripts/build_group_vectors.py att&ck_v14.json
  Used for: cosine similarity attribution scoring (Section 8.7)

18.5 INFERENCE PERFORMANCE TARGETS

  BERT ATT&CK (INT8 ONNX):        < 400ms per command  [hard limit 500ms]
  DistilBERT expertise:            < 200ms per command
  DCGAN traffic batch (30 pkts):   < 50ms
  ATT&CK cosine similarity (138):  < 5ms (NumPy vectorised)
  Total MT pipeline per command:   < 500ms (includes Redis publish)

SECTION 24 — ERROR HANDLING AND FALLBACK STRATEGY
================================================================================

24.1 PER-COMPONENT ERROR HANDLING

  ALL Python components:
    - Wrap entire main() in try/except
    - On unexpected exception: log to /backend/logs/{component}.log
    - Set health heartbeat to "error" state (HSET phantasm:system:health)
    - Continue running if possible (most errors are per-event, not fatal)
    - Never crash the process on a single malformed event

  NFQueue packet callback (sm_core.py):
    - If emulator raises exception: drop the packet, log the error
    - Never propagate exception to NFQueue (would halt packet processing)
    - Per-service error counter: if >10 errors in 60s → disable service emulator

  BERT inference (mt_classifier.py):
    - If ONNX inference fails: use keyword fallback with confidence=0.65
    - Log ONNX errors; switch to keyword-only mode if 3 consecutive failures

  Redis connection (all components):
    - Use redis-py's automatic reconnect: Redis(retry_on_timeout=True)
    - Backoff: 1s → 2s → 4s (exponential, cap at 30s)
    - During Redis outage: buffer events in memory (list, max 500 items)
    - Flush buffer on reconnect

  WebSocket disconnection (frontend):
    - Socket.io client reconnects automatically (reconnectionDelay: 1000ms)
    - On reconnect: emit "request_snapshot" to restore state
    - Buffer UI updates in-memory during disconnect; apply on reconnect

  LLM API failure (de_engine.py):
    - See Section 19.4
    - Fallback: cached narrative pre-generated for demo profiles
    - PDF still generates from cached narrative
    - Status: dossier:{sid}:status = "ready" (fallback is transparent)

24.2 DEMO RECOVERY PROCEDURES

  SCENARIO: NFQueue stops responding
    1. sudo iptables -D INPUT -i shadowmesh0 -j NFQUEUE --queue-num 1
    2. sudo iptables -I INPUT -i shadowmesh0 -j NFQUEUE --queue-num 1
    3. pkill -f sm_core.py && sudo python sm_core.py
    Recovery time: ~30 seconds

  SCENARIO: Redis crashes
    1. docker-compose restart redis
    2. All components auto-reconnect (retry backoff)
    3. Session continues from buffered in-memory state
    Recovery time: ~10 seconds

  SCENARIO: Frontend WebSocket disconnects
    1. Socket.io auto-reconnects within 3-5 seconds
    2. State restored via "state_snapshot" event
    Recovery time: ~5 seconds (invisible to judges in most cases)

  SCENARIO: BERT inference too slow (>1 second)
    1. Edit mt_engine.py: set USE_KEYWORD_FALLBACK_ONLY=True
    2. Restart mt_engine.py
    3. Classification still works, just with keyword matching
    Recovery time: ~10 seconds

SECTION 26 — SECURITY CONSTRAINTS FOR PHANTASM ITSELF
================================================================================

26.1 MANAGEMENT INTERFACE ISOLATION

  ALL PHANTASM management interfaces bind to 127.0.0.1 only:
    FastAPI:   uvicorn --host 127.0.0.1 --port 8000
    ShadowMesh: --host 127.0.0.1 --port 8001
    React dev: vite --host 127.0.0.1 --port 3000
    Redis:     127.0.0.1:6379 (Docker port mapping to loopback)

  ShadowMesh's attacker-facing interface is shadowmesh0 (a separate dummy
  network interface), not any localhost port.

26.2 NO REAL CREDENTIALS ANYWHERE

  PHANTASM codebase, configuration files, and generated outputs must contain
  ZERO real credentials or real PII. This is enforced by:
    - All AD passwords drawn from weak_passwords.json (known templates)
    - All NTLM hashes generated from deterministic synthetic formula
    - All customer data generated by Faker with no connection to real individuals
    - ANTHROPIC_API_KEY in .env (gitignored, never hardcoded)

26.3 ATTACKER-FACING vs MANAGEMENT TRAFFIC

  The NFQueue hook only processes packets arriving on shadowmesh0 interface.
  Packets on lo (localhost) or eth0 (real management NIC) are never queued.
  The iptables rule explicitly names -i shadowmesh0.

26.4 PROCESS ISOLATION

  ShadowMesh runs as root (required for NFQueue).
  All other processes run as non-root user.
  sm_core.py drops supplementary privileges after binding NFQueue:
    import prctl
    prctl.set_proctitle("phantasm-shadowmesh")
    # After NFQueue bind: drop CAP_NET_ADMIN where possible

SECTION 27 — DATA INTEGRITY AND ETHICAL COMPLIANCE
================================================================================

27.1 THE SYNTHETIC DATA GUARANTEE

  Every table that stores generated (non-attacker) data carries:
    is_synthetic BOOLEAN DEFAULT TRUE

  The iocs table is the sole exception — it stores real attacker observables.
  is_synthetic BOOLEAN DEFAULT FALSE is set only in the iocs table.

27.2 REAL DATA STORED BY PHANTASM

  PHANTASM stores the following real (non-synthetic) data:
    - Attacker source IP and port (iocs table, sessions.attacker_source_ip)
    - Raw command strings as typed by the attacker (commands.raw_command)
    - C2 callback IPs, domains, payload hashes (iocs table)
    - Timestamps of all activity

  Nothing else corresponds to real individuals, real accounts, real
  credentials, or real network infrastructure.

27.3 SYNTHETIC NTLM HASH SAFETY

  NEVER generate or store real NTLM hashes.
  Synthetic hash formula:
    hash = hashlib.md5(
        f"{session_id}{username}PHANTASM_SYNTHETIC_SALT".encode()
    ).hexdigest()

  This produces a valid 32-character hex format but is NOT a real NTLM hash.
  It CANNOT be used in pass-the-hash attacks against real systems.
  The PHANTASM_SYNTHETIC_SALT constant is stored in .env.

27.4 TLP CLASSIFICATION FOR IOCs

  All IOCs default to TLP:AMBER (organisational sharing only).
  CERT-In submission would require analyst review before upgrading to TLP:GREEN.
  shared_with_cert flag (default FALSE) tracks submission status.

27.5 LEGAL COMPLIANCE

  PHANTASM operates under India's IT Act 2000 / 2008 amendments.
  Honeypot operation is legal on organisational infrastructure.
  PHANTASM does not: access attacker systems, execute offensive code, or
  store real personal data. These constraints must be maintained in all code.

APPENDIX B — KNOWN RISKS AND MITIGATIONS (TECHNICAL)
================================================================================

RISK: NFQueue requires root — entire ShadowMesh runs as root
  MITIGATION: sm_core.py drops unnecessary capabilities after binding.
  Acceptable: demo is on a controlled machine, not production.

RISK: BERT inference exceeds 500ms budget on slow CPU
  MITIGATION: INT8 quantisation + keyword fallback.
  Measured pre-demo on target hardware.

RISK: WeasyPrint font download fails (no internet during demo)
  MITIGATION: Pre-download Inter font to /backend/static/fonts/.
  Reference via local @font-face in CSS template.

RISK: Multiple simultaneous command events overwhelm mt_engine
  MITIGATION: asyncio.Queue with bounded depth (max 100 items).
  Items older than 10 seconds dropped with warning log.
  Demo involves a single attacker at human typing speed — not a realistic
  risk, but must be handled.

RISK: D3 force simulation causes jank with 25 nodes
  MITIGATION: Fix layout of base 15 nodes. Only re-simulate the 3-8 new
  mutation-added nodes using a localised force with a smaller alpha.
  Max graph nodes: 25.

RISK: SQLite WAL file grows large during long test sessions
  MITIGATION: PRAGMA wal_checkpoint(TRUNCATE) called after each session ends.
